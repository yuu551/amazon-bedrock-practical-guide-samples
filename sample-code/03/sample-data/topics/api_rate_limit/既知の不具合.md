# APIレート制限の既知の不具合

SampleConnect APIレート制限まわりで現在報告されている既知の不具合と回避策をまとめます。修正完了次第、本ドキュメントの該当エントリは「修正済み」セクションに移動します。

## CL-RL-2026-002: バーストカウントの一時的な過剰消費

**症状**: 短時間（100ms以内）に多数のリクエストを送信すると、`X-RateLimit-Remaining` の減少量が実際の消費数より多くカウントされる場合があります。最大で実際の1.2倍程度まで多めに減少します。

**影響範囲**: 全プラン。特にバッチエンドポイントを高頻度で呼び出すケース。

**回避策**: クライアント側で同時実行数を制御し、100ms以内の集中送信を避けてください。`X-RateLimit-Remaining` ではなく、自前のローカルカウンタで管理することも有効です。

**修正予定**: 2026年6月のメンテナンスで対応予定です。

## CL-RL-2026-001: Retry-After ヘッダの最大値表記揺れ

**症状**: 24時間累計の自動停止（HTTP 503）時のレスポンスヘッダ `Retry-After` に、停止解除までの正確な秒数（最大21,600秒 = 6時間）ではなく、上限値である86400秒が返却される場合があります。

**影響範囲**: 24時間累計超過による自動停止状態のアカウントのみ。

**回避策**: `Retry-After` の値が3,600秒を超える場合は、6時間（21,600秒）として再試行スケジュールを組んでください。

**修正予定**: 2026年5月のメンテナンスで対応予定です。

## CL-RL-2025-012: WebhookのRetryカウントが多重計上される

**症状**: Webhook送信エラー時の自動再送（最大3回）が、まれに4回以上カウントされる場合があります。再送上限を超える送信が発生することはなく、ログ表記のみの問題です。

**影響範囲**: 管理コンソールのWebhook送信履歴の表示のみ。実際の送信回数は規程通り3回です。

**回避策**: 表示上は4回でも、実際の送信は3回までに収まっています。ログをカウントとして集計する場合は、`attempt_id` でユニークカウントしてください。

**修正予定**: 2026年5月のメンテナンスで対応予定です。

## 修正済み

### CL-RL-2025-008: 上限緩和の即時反映が実装と仕様で乖離

**症状**: 上限緩和申請の承認後、規程上は72時間以内に有効化と記載していたが、実装は手動オペレーションで承認後最大1週間かかっていた。

**修正日**: 2025年11月15日

**修正内容**: 承認時に自動で有効化処理を実行する仕組みを追加。承認後24時間以内に有効化される運用に改善。規程の72時間表記は変更せず、より短いリードタイムで運用しています。

### CL-RL-2025-005: バッチエンドポイントが2倍カウントされる

**症状**: `/v1/batch/*` エンドポイントが、想定の1リクエスト消費ではなく2リクエスト消費としてカウントされていた。

**修正日**: 2025年9月3日

**修正内容**: バッチエンドポイントの内部処理見直し。1リクエスト消費に修正。
