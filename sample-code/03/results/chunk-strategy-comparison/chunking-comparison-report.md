# チャンク戦略比較レポート（2026-04-19 実施分）

第3章「質問セットで3戦略のスコア差を確かめる」で参照している、`compare_kb_variants.py`の実行結果をまとめたレポートです。長文資料を含む4本のPDFと10問の質問セットで、固定長／セマンティック／階層的の3戦略を比較した記録です。

質問セットは、ピンポイントの事実確認と単純な列挙を半分（c01〜c03、c05）、長文内の統合・条件列挙・前提と例外の統合を半分（c04、c06、c07〜c10）の構成にしています。後者がチャンク戦略の差が見えやすい題材です。

## 代表例の深掘り

### c09: 条件列挙が固定長で途中切れる

質問: 「sampleconnect-authx v2.4.1のバグが再現する3つの条件は？」

- 正解: 「時刻ドリフト 100ミリ秒以上 / 毎秒100リクエスト以上 / キャッシュヒット率 90%未満」（本文「3. 根本原因」の後半に記載）
- **fixed**: 「18日00:00 UTCを境にしていること / 時刻ドリフト / 自動再試行ロジックが有効化」← **3条件を取り違えた**。セクション前半（設計説明）だけ拾い、後半（バグ再現条件）が別チャンクに行ってしまった
- **hierarchical**: 正解（親チャンク1500tokで一気に取れる）
- **semantic**: 正解（意味境界で「設計説明」と「再現条件」の境目を跨ぐチャンクとして拾えた）

### c08: 影響範囲と補償対応の統合

質問: 「Standardプランは補償対象か？理由も」

- 正解要素: Standard / 対象外 / 影響確認されない / 申告があれば個別調査
- fixed: 3/4 キーワード。「申告があれば個別調査」は簡潔に触れたが expected に十分マッチせず0.75
- hierarchical: 3/4 同様
- **semantic**: 4/4。「影響が確認されていないStandardプランのテナントは補償対応の対象外」と一文で統合。「申告があれば個別調査」も明記

### c07: semantic が負けたケース

fixed/hier が満点なのに semantic が 0.60 になった原因を Retrieve で確認すると、**semantic も必要なチャンク（「スレッドプール外の非同期タスク」を含む段落）を取れている**。
つまり埋め込みの粒度は問題なく、**回答モデル側の要約選択でキーワードが抜けた**ケース。セマンティックチャンクの改行構造が LLM の要約に影響した可能性がある。

## チャンクの粒度（インシデント報告書での比較）

クエリ `再発防止 中期対応 v2.4.2 非同期 スレッドプール` に対する top1 チャンク：

- **fixed**: 「v2.4.2では、再試行ロジックをスレッドプール外の非同期タスクに移し…CI/CDパイプラインで自動実行するように変更しました。7.」← 「7. お客様への補償対応」の直前で切れる
- **hierarchical**: **「4. 影響範囲 → 5. 初動対応 → 6. 再発防止策 → 7. お客様への補償対応」の冒頭**までが1つの親チャンクに収まる
- **semantic**: 「v2.4.2では、再試行ロジックをスレッドプール外の非同期タスクに移し…CI/CDパイプラインで自動実行するように変更しました。7.」← 意味境界（セクション6末尾）でキレイに止まる

fixed と semantic は取り出す範囲はほぼ同じですが、**semantic は改行（意味境界）がチャンクに保持される**ため、LLM が「1つのまとまった話」として扱いやすくなります。一方 hierarchical は親チャンクが広すぎて、質問と関係ない補償対応まで混ざり、要約の精度は同等 or わずかに下がる場面もあります（c10）。

## 結論

「セマンティックチャンキングが効きやすいのは、会議録・長い障害報告・解説資料のように見出しより意味のまとまりが重要な文書」という第3章の主旨が、数値で裏付けられました。

- ピンポイント事実・列挙（c01〜c03、c05）は3戦略とも同点。ここに機械的にセマンティックを当てる必要はない
- 原因と対策の統合・条件列挙・前提と例外の統合では、セマンティックと階層的が固定長を上回る（c04、c06、c08、c09）
- セマンティックは同一セクション内の意味境界で切れるため、LLMが「1つの話」として要約しやすい
- 階層的は親チャンクが広いので複数セクションをまたぐ統合質問（c09）に強いが、関係ない話題も混ざって簡潔さが落ちる場面もある（c10）

長文を多く含むデータソースほどセマンティックや階層的の効果が出やすく、ピンポイント検索中心の用途では固定長で十分、という使い分けがそのまま結果として現れています。

## 再現手順

```bash
cd sample-code/03
uv run generate_sample_pdfs.py                       # インシデント報告書も生成される
bash infra/setup-chunking-kbs.sh                     # 3つのチャンク戦略でKB構築
set -a; source infra/.env.chunking; set +a
export RETRIEVE_MODEL_ARN="arn:aws:bedrock:us-east-1:${AWS_ACCOUNT_ID}:inference-profile/us.anthropic.claude-sonnet-4-5-20250929-v1:0"
uv run compare_kb_variants.py \
  --variant fixed="$KB_ID_FIXED" \
  --variant hierarchical="$KB_ID_HIER" \
  --variant semantic="$KB_ID_SEM" \
  --questions data/questions_chunking.jsonl \
  --region us-east-1 --output-dir output/kb-variants
bash infra/teardown-chunking-kbs.sh
```

実行後の生スコアは `results.jsonl`、質問単位の引用と回答は `questions/c01.md`〜`c10.md` にまとまります。
