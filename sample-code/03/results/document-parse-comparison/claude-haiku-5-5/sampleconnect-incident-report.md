# SampleConnect Platform 2026年3月18日 API停止障害 詳細報告書

発生日: 2026年3月18日（火） 13:05 JST〜14:47 JST（約1時間42分）。影響: 一部テナントにおけるSampleConnect API応答停止。本報告書は、営業担当および技術担当のお客様向けに、原因と対策、影響範囲、再発防止策を段階的に説明します。

## 1. インシデント概要

2026年3月18日13:05 JSTから、SampleConnect Platformの `/v1/search` および `/v1/agent` エンドポイントで、一部テナントに対するAPI応答が断続的に停止する事象が発生しました。影響範囲はEnterpriseプラン契約の一部テナント、特に米国東部リージョン（us-east-1）にベクトルデータを配置しているテナントに集中しました。通常の運用監視で検知した後、オンコール体制による対応に移行し、14:47 JSTに全テナントで完全復旧を確認しました。本報告書の前半では事実関係と原因を、後半では再発防止策と補償対応を記載しています。

## 2. タイムライン

13:05 JST: 特定テナントの `/v1/search` で 5xx応答が断続発生。内部メトリクスでエラーレートが1.2%から18.4%まで急増。13:09 JST: オンコールエンジニアが自動ページングを受領し一次対応を開始。13:16 JST: 認証トークンの検証レイヤで `ExpiredToken` 例外が大量発生していることを確認。13:28 JST: 認証サービスの内部キャッシュをフラッシュする手順を実行したが症状は改善せず、さらに別のレイヤで障害が起きている可能性を検討。13:42 JST: OpenSearch ServerlessへのSigV4署名生成に用いる共有ライブラリが、18日00:00 UTCからの時刻同期ずれで一部ノードでリクエストを拒否していたと判明。14:05 JST: 影響ノードのローリング再起動を開始。再起動中のテナントでは一時的に応答遅延が発生することをサポート窓口から案内。14:31 JST: ローリング再起動完了。エラーレートが平常値（0.04%）まで低下したのを確認。14:47 JST: 全リージョンで監視ダッシュボード上のSLOを満たしたことを確認し、全面復旧を宣言。

## 3. 根本原因

根本原因は、SigV4署名生成に用いる共有認証ライブラリ `sampleconnect-authx` v2.4.1 のバグです。このバージョンは、18日00:00 UTCを境にシステムクロックと認証トークンの発行時刻に100ミリ秒以上のドリフトが発生すると、署名検証を自動再試行するロジックが有効化される設計でした。再試行は最大3回行われ、それでも失敗するとフォールバックとしてトークンを無効化します。しかし、実装上の欠陥により、再試行ロジックが無効化判定を終えるまで該当リクエストがブロックされ、結果としてスレッドプールが枯渇しました。

このバグは、通常の単体試験および負荷試験では再現しませんでした。再現条件は、(1) 時刻ドリフトが100ミリ秒を超えること、(2) 同一テナントから毎秒100リクエスト以上の並行トラフィックがあること、(3) キャッシュヒット率が90%未満に低下していること、の3条件が同時に成立することです。本番環境の特定テナントでこの条件がそろいました。なお、Standard / Freeプランのテナントは独立したスレッドプールを利用しているため影響を受けませんでした。

## 4. 影響範囲

影響を受けたのは、Enterpriseプランに契約しているテナントのうち、以下の条件をすべて満たすテナントに限られます。(A) us-east-1リージョンにベクトルデータを配置していること、(B) 13:00〜14:30 JSTの時間帯に `/v1/search` または `/v1/agent` への並行リクエスト数が毎秒100以上あったこと、(C) 専用SigV4キャッシュを有効化していること（デフォルト有効）。なお、Standard / Freeプランのテナント、および他リージョン（us-west-2、ap-northeast-1）にデータを配置していたテナントは影響を受けていません。さらに、Enterpriseプランでも上記(B)の条件を満たさない（低トラフィック）テナントは、自動再試行の範囲内で応答が返却されていたため体感上の停止は発生していません。

## 5. 初動対応と復旧手順

初動では、オンコールエンジニアが認証トークンの異常を疑い、キャッシュフラッシュを実施しました。この手順は過去の類似事象で有効だったため最初に試みましたが、今回のケースでは原因レイヤが異なっていたため効果がありませんでした。続いてSigV4署名エラーのログパターン解析を行い、時刻ドリフトとの相関を特定したうえで、影響ノードのローリング再起動を決定しました。

ローリング再起動の具体的な手順は次のとおりです。まず、負荷分散層（ALB）でunhealthy判定となっているノードを切り離します。次に、該当ノードで `sampleconnect-authx` を v2.4.1 から v2.3.9 へロールバックし、ローカルキャッシュをクリアしたうえでサービスを再起動します。ノードの再起動後にヘルスチェックが通ることを確認したら、ALBに戻します。この作業を1ノードずつ順次実施し、30分で12ノードの切り替えを完了しました。並行して、サポート窓口から影響テナントへ「応答遅延が発生する可能性あり」の案内を送信しています。

## 6. 再発防止策

短期対応として、 `sampleconnect-authx` を v2.3.9 にロールバックし、問題のあった自動再試行ロジックを無効化しました。この対応は本障害の2時間後、3月18日17:00 JSTまでに全ノードへ適用完了しています。ただし、v2.3.9では時刻ドリフト時の自動復旧機能がないため、中期的な解決にはなりません。

中期対応として、 `sampleconnect-authx` v2.4.2 を4月末までにリリースします。v2.4.2では、再試行ロジックをスレッドプール外の非同期タスクに移し、スレッドプール枯渇を防止します。v2.4.2は、v2.4.1と同じ自動復旧機能を持ちながらも、今回の障害パターンに耐える設計に変更されています。長期的な再発防止としては、時刻ドリフト検知をNTP層で閉じ込め、認証レイヤまで伝播しない構造を5月の定期リリースで導入する計画です。また、負荷試験では時刻ドリフトをシミュレートするテストケースを新規に追加し、CI/CDパイプラインで自動実行するように変更しました。

## 7. お客様への補償対応

EnterpriseプランのSLA（99.95%）に基づき、影響を受けたテナントに対してはSLAクレジットを自動適用します。具体的には、3月度の月額利用料の10%をクレジットとして翌月請求から減算します。対象テナントには3月24日までに個別にメール通知を送付しています。Standard / Freeプランのテナントについては、今回の障害による影響が確認されていないため、補償対応の対象外としています。ただし、Standardプランで今回の事象に類似する応答遅延を観測したテナントからの申告があった場合は、サポート窓口で個別に調査します。なお、この補償対応はSLA契約書の第14条および別紙「障害対応規程」に準拠した内容であり、特例措置ではない通常のフローに従った運用です。
